# SQL 构建与验证工作流

本文件把 SQL 从“能执行”提升到“结果可证明正确”。适用于取数、聚合、留存、漏斗、事件分析、PSM/DID、导出和对账。AGENTS.md 中的规则与本文件同时生效。

## 1. 先写结果契约

在写 SQL 前，先用一小段文字定义以下内容：

| 项目 | 必须写清的内容 |
| --- | --- |
| 业务问题 | 要回答什么判断，而不是只说“跑个表” |
| 样本总体 | 平台、品类、主播、用户、区域、有效条件 |
| 时间口径 | 源数据范围、事件窗口、观察窗口、实际可用分区 |
| 基础粒度 | 一行代表什么，例如用户日、主播日、用户月、订单 |
| 唯一键 | 例如 `(dt, pcode, category, user_id)` |
| 输出粒度 | 最终一行代表什么，例如 `mth + pcode + category` |
| 分子 | 具体事件、过滤条件和单位 |
| 分母 | 同一口径的基数，不能只是“总数” |
| 分组维度 | 哪些字段用于业务拆分，缺失值如何处理 |
| 预期规模 | 最多多少行、关键分组数量、分母大致量级 |
| 已知限制 | 字段字典、权限、覆盖缺口、不可观测因素 |

结果契约不完整时，不得直接进入 SQL 实现。

除文字契约外，至少要预先写出一个可反驳的预期，例如“按月份重算的分母应完全一致”“join 前后事实行数应相同”“导出文件应为 120 行且表头与查询一致”。如果无法写出任何预期，说明尚未理解数据或业务结构，应先取字段、分区和小样，而不是先写完整 SQL。

## 2. 梳理数据与关联

1. 先查看源表 DDL、字段含义、分区格式、单位、可空性、枚举值和时间覆盖。
2. 在事实表侧先完成分区和业务过滤，再与小维表关联。
3. 每个关联键都要先分别验证唯一性，不得把多对多关联当成一对一。
4. 每个 join 都必须写出预期关系：`1:1`、`N:1`、`1:N`、`N:N`，以及预期行数是否变化。
5. 明细表放大后再求和、去重或算比例，是最常见错误来源；必须先确定聚合和展开顺序。

## 3. SQL 实现方式

1. 使用职责清晰的 CTE，至少区分过滤、粒度规整、映射、展开、匹配和最终聚合。
2. 每个关键 CTE 注释三件事：输入粒度、输出粒度、是否允许放大行数。
3. 不要在明细粒度上直接算业务比例；先分别得到可独立复算的分子和分母组件。
4. 分子与分母使用同一业务过滤和同一 cohort；不同窗口共享分母时，必须明确哪些来源完全相同。
5. 长表展开时检查预期倍数；宽表标志转换时检查目标键唯一。
6. 对任意比率，明确分母为 0 时返回空值、0 还是排除该分组，不能用隐式行为代替业务决定。
7. 关键结果尽量保留可独立复算的分子、分母和中间计数，避免把业务逻辑藏在一个巨大表达式里。

## 3.1 先做风险画像

不要只用一张通用清单平均检查所有 SQL。实现前先判断本任务最可能错在哪里，再把对应验证设为必跑项：

| 风险场景 | 必须预先定义 | 最低验证证据 |
| --- | --- | --- |
| 留存、漏斗、多窗口 | cohort 粒度、共同分母、目标日映射 | 各窗口分母一致；独立复算逐组分对账；一个展开 N 行仍只计 1 个基数的反例 |
| 多表 join | 两侧唯一键、匹配率、基数、预期乘数 | join 前后行数、最大匹配次数、未匹配样本；一对多必须解释 |
| 事实表关联过滤 | 过滤应落在事实表侧还是关联条件 | 将过滤移到事实 CTE 前后对比，核对未匹配和行数 |
| 时间窗/事件前后 | 事件闭区间、N 个自然日或有效日、实际分区 | 日期边界、缺失分区清单、可观察 cohort 排除规则 |
| 金额/时长/ACU | 原字段单位、转换关系、聚合方式 | 最小值/最大值/分位、单位反例、汇总值与分子分母重建 |
| 去重/取最新 | 业务主键、排序键、并列规则 | 去重前后行数、并列键数量、确定性排序结果 |
| `union all`/展开 | 来源粒度、输出粒度、预期倍数 | 各分支行数、唯一键、展开前后倍数 |
| PSM/DID/PSM-DID | 样本资格、处理时点、匹配特征、前后窗 | 匹配前后样本量、平衡性、平行趋势、口径表与结果表对账 |
| Excel/CSV 导出 | 字段名、行数、编码、ID 类型 | 查询结果与导出文件三方对账；中文和长 ID 回读检查 |

风险画像与结果契约应在执行记录中留痕。场景命中但没有对应证据时，状态只能是“未执行”，不能写成“已验证”。

## 3.2 写完后的第一轮静态审查

SQL 写完后不要立即把“执行成功”当成结论。先逐项静态审查，确认最容易被模型自行补全或忽略的语法和行为：

1. 过滤位置：事实表分区和业务条件是否在事实 CTE 内；把右表过滤写进 `left join` 的 `on` 还是放在 `where`，是否符合保留未匹配行的意图。
2. NULL 与零值：`count`、`sum`、`avg`、除法和 `coalesce` 是否把“没有数据”误转成 0；分组键为 NULL 时是否应保留未知组。
3. 时间边界：日期字段是字符串还是日期；起止区间是否明确包含两端；留存 D7 是 T+6、T+7 还是有效日第 7 天；时区是否一致。
4. 窗口函数：`partition by`、`order by`、frame、并列排序和 `row_number`/`rank` 的选择是否与业务一致。
5. 去重顺序：先去重再 join、先 join 再聚合还是先聚合再 join；`distinct` 的粒度是否与最终唯一键一致。
6. join 语义：关联键类型是否一致；是否把非关联过滤条件写进 join；`left join` 后是否又用右表字段过滤掉了未匹配行。
7. 集合与展开：`union all` 两边列数、顺序和类型是否一致；展开或 unpivot 后是否产生预期倍数。
8. 比率与口径：分子分母是否来自同一 cohort；分子是否可能因重复行被放大；分母是否被展开后的行数错误放大；零分母是否显式处理。
9. 硬编码与依赖：日期、游戏 ID、上限、快照分区、表名和阈值是否适用于当前任务；是否复用了别的周或别的项目的调试值。
10. 可读性与可复现性：字段别名是否稳定；关键 CTE 是否可单独运行并带粒度注释；是否存在会改变语义的隐式类型转换。

静态审查只能发现问题，不能证明结果正确。每一项高风险检查仍必须有执行结果作为证据。

## 4. 八类验证闸门

每类都必须给出查询、结果和状态：`通过`、`失败` 或 `未执行`。任何“失败”都必须修复；“未执行”不得写成“已验证”。

### 4.1 数据可用性

- 最新实际可用分区、目标结束日、缺失日期。
- 关键源表是否为空，分区是否存在，是否只存在表但没有目标日期。
- 事件日与目标观察日是否完整；缺分区和没有行为必须分开。

### 4.2 Schema 与语义

- 字段名、数据类型、单位是否符合预期，例如分钟/小时、元/分、毫秒/秒。
- 枚举值、空字符串、NULL、小数、负数、重复事件是否合理。
- 业务字段含义未知时停止解释，不用猜测补字典。

### 4.3 粒度与唯一性

- 基础表按声明唯一键是否唯一。
- 最终表按输出键是否唯一。
- 聚合前后行数和去重前后行数是否符合预期。
- 关键 ID 是否保持字符串格式，未丢失前导零或被浮点化。

### 4.4 关联与行数放大

- 逐个 join 检查：左表行数、右表键唯一性、匹配率、匹配后行数、最大匹配次数。
- `N:1` 关联不应改变事实行数；若改变，必须解释。
- `1:N`、`N:N` 和行列展开必须给出预期放大倍数及唯一键。
- 对聚合后的风险口径，检查是否存在重复计人或重复计事件。

### 4.5 指标不变量

- 计数不为负，比率处于有效范围。
- 分子不大于分母；分项之和不大于总数，除非业务明确定义重叠。
- D7/14/30、拉新/回流、前后窗口等共同分母应满足明确的一致性条件。
- 总和与分组总和一致；均值应能从分子和分母重新推导。
- 注意：这些只是必要条件，不能单独证明分母正确。

### 4.6 独立复算与对账

- 至少用一种独立路径从基础粒度重算关键分子、分母或总量，再与最终结果逐分组精确比较。
- 独立路径应尽量少复用被验证的 CTE，避免同一个错误被重复实现。
- 对阶段表、目标表和导出文件做三方对账：行数、唯一键、指标、过滤范围。
- 修复旧 SQL 后，要把旧结果、新 SQL、新结果和差异原因同时记录；只有重跑和对账成功才算修复。

### 4.7 边界、敏感性与业务抽查

- 检查最小/最大日期、样本过少、分母过小、NULL、未知分组和极端值。
- 对关键阈值做敏感性检查，说明结论是否依赖任意业务假设。
- 人工抽查至少 3 至 5 个基础单位，沿来源、join、聚合到最终值逐层核对；留存至少抽查一个“留存”和“未留存”案例。
- 检查结果方向是否符合业务常识；不符合时优先怀疑口径和代码，而不是强行解释。

### 4.8 交付与运行检查

- 实际执行是否完成，是否出现隐式类型转换、资源超限、超时、部分结果或权限报错。
- 阶段表、目标表、导出文件与报告是否在行数、唯一键、指标、分组和过滤范围上一致。
- SQL 结果表头与导出文件表头是否一致；长 ID 是否仍是字符串；中文编码、空行、空列和格式化数值是否正常。
- 目标表重跑是否幂等，是否存在重复写入、覆盖错误、分区漏写或旧结果残留。
- 记录实际引擎、时间范围、运行耗时或已知性能风险、输出路径和失败项影响；不能把“能跑完”单独当作性能或正确性证明。

## 5. 可复制执行记录

开始写 SQL 前，先在任务说明或交付文档中填写：

```text
业务问题：
样本与时间：
源表与最新分区：
基础粒度与唯一键：
中间粒度：
输出粒度与唯一键：
分子定义：
分母定义：
join 关系与预期行数变化：

可反驳的预期结果：

```

执行后至少填写以下记录；证据列写查询编号、SQL 文件、结果文件或关键结果，不能只写一句“已检查”。

| 验证闸门 | 检查内容 | 证据 | 状态 | 关键数字或差异 |
| --- | --- | --- | --- | --- |
| 数据可用性 | 分区、日期覆盖、空表 |  | 通过/失败/未执行 |  |
| Schema 与语义 | 字段、类型、单位、NULL |  | 通过/失败/未执行 |  |
| 粒度与唯一性 | 聚合前后行数、唯一键 |  | 通过/失败/未执行 |  |
| 关联与放大 | 基数、匹配率、放大倍数 |  | 通过/失败/未执行 |  |
| 指标不变量 | 分子/分母、范围、汇总一致 |  | 通过/失败/未执行 |  |
| 独立复算 | 独立路径逐分组对账 |  | 通过/失败/未执行 |  |
| 边界与抽查 | 日期边界、小样本、人工案例 |  | 通过/失败/未执行 |  |
| 交付与运行 | 阶段表/目标表/导出/报告、表头、编码、幂等性、性能 |  | 通过/失败/未执行 |  |

交付前最后回答六个问题：

1. 最终一行代表什么，是否仍符合结果契约？
2. 每个 `join`、展开或去重是否改变了预期行数？
3. 分母是否从基础粒度独立重算，而不是复用被验证的同一段逻辑？
4. 结果是否已与目标表、阶段表和导出文件对账？
5. 哪些检查没有运行，它们分别影响哪个结论？
6. 实际执行和交付链路是否满足类型、编码、幂等性和性能约束？

## 6. 交付格式

每次正式 SQL 交付至少包含：

1. 可执行 SQL。
2. 独立验证 SQL 或验证步骤。
3. 结果契约和已知限制。
4. 实际使用的引擎、时间范围、输出路径、运行耗时或已知性能风险。
5. 各项校验的状态和关键数字。
6. 未执行或无法验证的事项。
7. 阶段表、目标表、导出文件和报告的对账结果。

只提供 SQL 而不提供验证证据可以用于草稿，不能标记为“已验证”。

## 7. 失败后必须做模式复盘

发生错误时，不只修当前 SQL，还要记录：

1. 错误现象和最终业务影响。
2. 根因属于需求、口径、粒度、关联、展开、窗口、类型、权限还是实现。
3. 哪个校验本应提前发现它，为什么当时没有触发。
4. 新增或修订的规则、验证 SQL 或测试样例。
5. 是否已有其他 SQL 复用同一错误模式，列出排查范围。

把修复写成可执行检查或最小样例，例如“长表展开后各窗口分母必须逐月相等”“事实表经过用户维表后行数不得变化”。如果只是把“要仔细检查”再加进规则，下次仍可能凭主观感觉跳过；可执行证据才有防复发作用。

连续出现同类错误时，必须回到上游设计检查：是否缺少字段字典、是否在错误粒度上写聚合、是否把 join 当成了一对一、是否用同一个错误 CTE 做了所谓“复核”、是否没有运行独立复算、是否导出后没有回读。不要只追加一条更长的提示词。
