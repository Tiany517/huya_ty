# 反挖估算模型与校验说明

## 1. 历史问题和输出

历史任务的业务目标是从外部平台主播特征中筛选值得进一步关注的候选人，并给出虎牙侧 ACU、拉新、收入特征和月薪的粗估。四个输出字段都不是实测值：

| 字段 | 历史含义 | 公式或方式 | 可信边界 |
| --- | --- | --- | --- |
| `predict_acu` | 虎牙 ACU 预测 | 多个外部特征按参考主播缩放，加权并按平台系数调整后取整 | 硬编码启发式；没有样本外误差 |
| `predict_laxin` | 虎牙拉新预测 | 斗鱼/B站使用另一组权重和系数；抖音/快手直接复用 ACU 函数 | 不等于真实拉新 |
| `predict_yingshou` | 收入特征 | `ACU×8×0.2 + gift_user×50×0.2 + gift_value×0.6` | 周期和金额单位未定义；任一礼物字段缺失时整行为 0 |
| `predict_pay` | 月薪估算 | 月观看小时=`ACU×20×5.5`，再按品类分段边际费率累计 | 依赖开播天数和时长假设；不是市场工资 |

## 2. 输入粒度与字段

斗鱼/B站输入一行代表一个外部主播在业务快照中的特征记录，历史唯一组合为 `uid + pcode + r_category`：

```text
r_owner, uid, pcode, r_category, liucun, avg_com, danmu, fans,
dingyue_add, danmu_only, danmu_new, live_mins, gift_user, gift_value
```

抖音/快手输入使用：

```text
r_owner, uid, pcode, r_category,
online_0, online_10, online_20, online_30,
onlineu_0, onlineu_10, onlineu_20, onlineu_30,
fans, fans_add, live_hours, live_dt
```

`06allres.csv` 共 34,309 行，`featt` 与它的 14 个基础字段完全一致，`res.txt` 的 14 个基础字段也完全一致。`06allres.csv` 只含 B站 29,975 行、斗鱼 4,334 行；抖音和快手的最终输出没有随目录留下。

## 3. 计算公式概要

### 3.1 斗鱼 / B站

每个外部信号先用三个参考量做二维映射：

```text
candidate_score = (value / ref_low × 15900
                 + value / ref_mid × 3755
                 + value / ref_high × 1800) / 3
```

再按各平台、各字段的上限截断。`predict_acu` 对评论、弹幕、订阅、仅弹幕和新增弹幕分别计算分数，按权重相加，再乘平台缩放系数并四舍五入到 50。

| 平台/版本 | 缩放 | 权重（评论/弹幕/订阅/仅弹幕/新增弹幕） |
| --- | ---: | --- |
| 斗鱼常规 | 1.0；DOTA2 为 1.2 | 0.40 / 0.30 / 0.05 / 0.15 / 0.10 |
| 斗鱼拉新 | 1.4 | 0.45 / 0.15 / 0.05 / 0.20 / 0.15 |
| B站常规 | 0.38 | 0.40 / 0.30 / 0.05 / 0.15 / 0.10 |
| B站拉新 | 0.70 | 0.15 / 0.15 / 0.15 / 0.35 / 0.20 |

### 3.2 抖音 / 快手

抖音用 0、10、20、30 四个在线人数序列，以 `0.1 / 0.35 / 0.35 / 0.20` 加权；普通在线人数占 30%，去重在线人数占 70%。粉丝大于 10 时再加入粉丝总量和粉丝增量。最后乘 `0.83` 并按 10 取整。

快手使用去重在线人数序列，以同一组时间权重合成，再乘 `0.8 × 0.85 × 0.85` 并按 50 取整。

### 3.3 月薪

品类小时费率是 8 段累计边际费率，累计观看小时超过阈值后，只有新增部分使用下一档费率。原脚本假设每月 20 个开播日、每日 5.5 小时。品类未命中时使用“全品类”费率。

## 4. 已知实现缺陷和解释限制

1. `danmu_new` 的最终上限使用 `danmu_only` 得分，而不是该字段自己的得分；这会让新增弹幕信号失去独立作用。原脚本保留，仓库版本也保留，仅添加注释。
2. 抖音 `predict_acu` 与 `predict_laxin` 调用同一函数，两个预测必然相同；没有历史文档证明这是业务设计。
3. 快手函数先计算一次普通在线序列结果但不使用，随后使用去重在线序列；仓库版只保留实际参与返回值的逻辑。
4. `predict_yingshou` 的缺失礼物字段会把整行收入置为 0，即使 ACU 非零；只能用于历史筛选，不可直接做财务汇总。
5. 参考主播、权重、上限和缩放系数是人工参数，缺少出处、拟合样本、时间版本和误差度量。
6. 输入与虎牙后续表现没有逐人 linked outcome，因此无法估计预测偏差、召回率或反挖收益。

## 5. 版本漂移与独立复算

历史最终表生成时间与脚本最后修改时间不一致。以当前归档脚本复算历史最终表得到：

| 检查 | 结果 | 状态 |
| --- | ---: | --- |
| `featt` 与最终 CSV 的 14 个基础字段 | 34,309 / 34,309 一致 | 通过 |
| `res.txt` 与最终 CSV 的 14 个基础字段 | 34,309 / 34,309 一致 | 通过 |
| 斗鱼 `predict_acu` | 4,334 / 4,334 | 通过 |
| B站 `predict_acu` | 29,975 / 29,975 | 通过 |
| 斗鱼 `predict_laxin` | 4,334 / 4,334 | 通过 |
| B站 `predict_laxin` | 23,262 / 29,975，77.605% | 警告：版本漂移 |
| 斗鱼 `predict_yingshou` | 4,334 / 4,334 | 通过 |
| B站 `predict_yingshou` | 29,975 / 29,975 | 通过 |
| 斗鱼 `predict_pay` | 4,328 / 4,334 | 6 行品类映射漂移 |
| B站 `predict_pay` | 29,961 / 29,975 | 14 行品类映射漂移 |

因此不能声称“当前代码完全等于历史结果”。历史排名的唯一可靠来源是当时的 `06allres.csv`；当前模块用于继续开发和重新验证。

## 6. 复用步骤

1. 恢复并核对源表 DDL、字段单位、NULL 编码、分区和最新日期。
2. 用 `fanwa_estimator.py` 在本地计算预测，不执行远端写表。
3. 逐平台、逐品类、逐人对照历史输出；任何差异先归因到参数、脚本版本或输入数据版本。
4. 若要形成招聘建议，补充真实后续结果并做样本外评估；至少报告覆盖率、误差、排序相关性、极端值和小样本情况。
5. 对候选名单加入人工复核和业务规则，不能仅凭 `predict_acu` 或月薪代理值做决定。
