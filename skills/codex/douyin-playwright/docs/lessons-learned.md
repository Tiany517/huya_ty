# 抖音数据抓取实战经验与设计规范

**日期**: 2026-06-25
**来源**: 首次实战测试（博主"黄士铨看世界"）复盘

---

## 一、核心教训

**不要把"能跑通"当成"能交付"**。过程中反复试错、环境踩坑、策略低效，说明在**鲁棒性、预检机制、降级策略**上还有很大改进空间。下次设计应先花 **20%时间做环境预检和容错设计**，再花 **80%时间做核心抓取逻辑**。

---

## 二、技术层面踩坑

| 问题 | 复盘经验 |
|:---|:---|
| **浏览器CDP操作慢** | 每次页面跳转2-3秒是硬开销，10个视频累积30秒+。优先用**批量API请求**代替逐个浏览器点击，或在Skill中标注"此步骤预计耗时X分钟" |
| **CSS选择器频繁失效** | 抖音DOM结构复杂且动态变化。**不要依赖深层CSS选择器**，改用基于**URL模式(/video/xxx) + 文本匹配(标题包含关键词)** 的定位策略 |
| **Windows路径陷阱** | `/tmp`实际映射到`C:\Users\...\AppData\Local\Temp`，`python3`不可用。执行前先做**环境探测**（检查python/python3、TEMP路径），避免中途报错 |
| **编码乱码** | 浏览器返回的中文标题在Python解析时乱码。**统一使用UTF-8编码读写文件**，避免跨系统编码不一致 |

---

## 三、流程层面缺陷

| # | 问题 | 改进方案 |
|:---|:---|:---|
| 1 | **缺少"预检"步骤** | 执行前先检查：浏览器可用 → python命令 → /tmp路径 → eval是否正常。**把环境问题的试错时间提前消化** |
| 2 | **数据获取策略低效** | 主页只显示点赞数，播放量/评论数需进详情页。**更优策略**：先批量获取主页所有可见数据（标题+点赞数+视频ID），然后**批量并发**访问详情页补全缺失字段，而非串行逐个访问 |
| 3 | **缺少降级机制** | 当eval多次报错时，应自动降级到**"截图+OCR识别"**或**"保存HTML本地解析"**，而非在同一方式上反复重试 |

---

## 四、Skill设计改进点

| 设计点 | 建议 |
|:---|:---|
| **环境预检** | Skill开头自动检测：Node.js/Chrome/CDP可用性、python命令、路径映射 |
| **数据兜底** | 当播放量/评论数获取失败时，输出已获取的数据 + 标注"需详情页获取"，而非阻塞整个流程 |
| **超时控制** | 每个视频详情页设置**5秒超时**，超时自动跳过，避免卡死 |
| **批量并发** | 优先用主页批量获取点赞数+标题+视频ID，然后用**并发请求**补全详情 |
| **编码处理** | 所有文件读写强制指定 `encoding='utf-8'` |
| **用户预期管理** | 在Skill文档中明确说明：抖音主页不显示播放量，需要额外步骤获取 |

---

## 五、关键设计决策

1. **环境预检自动化** — Skill执行前必须完成环境检查
2. **失败降级策略** — eval失败 → 截图OCR → 保存HTML本地解析，三级降级
3. **批量并发优化** — 主页批量获取 + 详情页并发补全
4. **跨平台兼容性** — Windows/Mac路径、编码统一处理
